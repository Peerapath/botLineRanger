# ระบบตรวจและสลับ App-Version / URL prefix อัตโนมัติ

วันที่: 2026-09-24 · สถานะ: อนุมัติดีไซน์แล้ว รอแผนลงมือ

## 1. เป้าหมาย

ให้บอทรู้เองว่าเซิร์ฟเวอร์ยอมรับ `App-Version` และ URL prefix (`/v12.3`) ค่าไหน แล้วสลับเองเมื่อค่าที่ใช้อยู่
ถูกปฏิเสธ — ใช้กับ **ทุกจุด** ที่บอทยิง `rangers-api.line-apps.com` ไม่มีใครฮาร์ดโค้ด `12.3.0` หรือ `/v12.3`
อีก และจำค่าที่ค้นเจอลงไฟล์ ให้รันครั้งหน้าเริ่มจากค่าที่ถูกทันที

ที่มา: วันนี้ `/signup/platform` เริ่มปฏิเสธ `App-Version 12.3.0` ด้วย 401 ทำให้ GenID สร้างบัญชีได้ 0 ใบ
โดยไม่มี error ใด ๆ บอกเหตุ ต้องไล่หาด้วยมือจนเจอว่า 12.2.0 ผ่าน (แก้ชั่วคราวใน `abd580e` ด้วย
`SIGNUP_APP_VERSION` ที่ฮาร์ดโค้ดไว้) ครั้งหน้าที่เกมอัปเดตจะเกิดซ้ำอีกแน่นอน

**สิ่งที่ห้ามเสีย:**

1. ตอนทุกอย่างปกติ **ห้ามยิงคำขอเพิ่มแม้แต่ครั้งเดียว** — Login mode ทำ 181 บัญชี/นาทีที่ 128 เธรด
   และชนเพดาน 80 req/s ของเราเองอยู่แล้ว
2. Login mode เจอโทเคนตาย (401) เป็นเรื่องปกติหลายพันครั้งต่อรัน — ห้ามให้ 401 เหล่านั้นกลายเป็นการสำรวจ
3. เก็บสถานะเป็นไฟล์ และยัง build เป็น .exe ได้ โมดูลใหม่ต้องผ่าน pyarmor และอยู่ใน `hiddenimports`
   เหมือน tools ตัวอื่น (ข้อกำหนดเดิม: ห้ามโค้ดใน `tools/` หลุดเป็น plaintext)
4. URL prefix **ย้ายเมื่อของเดิมพังเท่านั้น** — ผู้ใช้เลือกเอง (2026-09-24) เพราะ API เวอร์ชันใหม่อาจ
   เปลี่ยนรูปข้อมูลตอบกลับจนบอทอ่านผิดแบบเงียบ ๆ

## 2. หลักฐานที่ดีไซน์นี้ตั้งอยู่บน (วัดจริง 2026-09-24)

**signup** — ใช้ pending guest คนละใบต่อช่อง กันผลสำเร็จช่องหนึ่งปนเปื้อนช่องถัดไป:

| | header 12.3.0 | header 12.2.0 |
|---|---|---|
| URL `/v12.3/signup/platform` | 401 | 200 |
| URL `/v12.2/signup/platform` | 401 | 200 (×2) |

กวาด header อย่างเดียว: 11.9.0 / 12.0.0 / 12.1.0 / 12.2.9 / 13.0.0 → 400 `errorCode 119801`
(`extras.version` สะท้อนค่าที่ส่งไป), 12.2.0 → 200, 12.3.0 / 12.4.0 → 401

**business (`GET /v12.3/home` ด้วย LF_AC สดของบัญชีที่ GenID เพิ่งสร้าง):**

| ส่งอะไร | ผล |
|---|---|
| App-Version 12.3.0 / 12.2.0 / 12.3.2 / 12.4.0 | 200 |
| App-Version 12.1.0 / 11.9.0 | 400 `119801` |
| URL `/v12.3`, `/v12.2` | 200 |
| URL `/v12.4` | 404 `{"errorCode":400,"errorMessage":"<path>"}` |
| โทเคนปลอม + 12.3.0 | 401 `{"errorCode":401}` |
| **โทเคนปลอม + 11.9.0** | **400 `119801`** |

ข้อสรุปที่ดีไซน์ใช้:

- **เซิร์ฟเวอร์เช็กเวอร์ชันก่อนเช็กโทเคน** → ถามได้ฟรีว่า "รู้จักเวอร์ชันนี้ไหม" ด้วยโทเคนปลอม
  ไม่เสียบัญชี ไม่เสียโควตา mint (เรียกต่อไปว่า **oracle**)
- oracle แบบเดียวกันบอกได้ว่า prefix มีอยู่ไหม: 401 = route มีและถึงขั้นเช็กโทเคนแล้ว
- **"รู้จัก" ≠ "ยอมรับบน route นี้"**: 12.3.0 รู้จัก (business 200) แต่ signup ปฏิเสธ → oracle
  ตอบคำถามนี้ไม่ได้ ต้องลองคำขอจริง
- 401 ของ "signup ไม่รับเวอร์ชัน" กับ 401 ของ "โทเคนตาย" **หน้าตาเหมือนกันทุกไบต์** → ต้องแยกด้วยบริบท
  ไม่ใช่ด้วยเนื้อคำตอบ (ข้อ 4.3)

## 3. ส่วนประกอบ

### 3.1 `tools/client_version.py` (ใหม่)

หน้าที่เดียว: ตัดสินว่าคำขอนี้ต้องส่ง App-Version/prefix อะไร และเรียนรู้จากคำตอบ ไม่รู้จัก http.client
หรือ urllib — ผู้เรียกส่งฟังก์ชันยิงของตัวเองเข้ามา

```python
class VersionUnavailable(Exception): ...     # ไม่ใช่ SystemExit - ดูข้อ 5

def request(path: str, send, pinned_prefix: str | None = None) -> tuple[int, object]:
    """send(prefix: str, app_version: str) -> (status, parsed)  -- ผู้เรียกประกอบ header/url เอง
    คืน (status, parsed) ของคำขอสุดท้าย; อาจ raise VersionUnavailable"""

def headers(app_version: str) -> dict       # {"App-Version": ..., "User-Agent": ...}
def current() -> tuple[str, str]            # (prefix, app_version) ปัจจุบัน สำหรับ log/GUI
def describe() -> str                       # บรรทัดตอนเริ่มในข้อ 6
def on_switch(callback) -> None             # callback(msg: str) ทุกครั้งที่สลับค่า
def configure(path) -> ClientVersion        # engine_main เรียกตอนเริ่ม
def set_oracle(fn) -> None                  # rangers_api ลงทะเบียนตัวยิง oracle ตอน import
```

ทั้งหมดข้างบนเรียกผ่านอินสแตนซ์ `ClientVersion(path, oracle=None, learn=True)` ตัวหลักของโมดูล
เทสต์สร้างอินสแตนซ์ของตัวเองได้ และ `conftest.py` ที่รากโปรเจกต์ให้ทุกเทสต์ได้อินสแตนซ์ `learn=False`
ใน tmp_path พร้อม oracle ที่ล้มทันทีถ้าถูกเรียก — เทสต์เดิมที่มีตัวปลอมตอบ 401/404 จะได้ไม่เจอการยิงซ้ำ
หรือหลุดไปยิงเซิร์ฟเวอร์จริง

สถานะภายใน (ต่อโปรเซส ป้องกันด้วย lock เดียว):

- `app_version` — ค่าหลัก ค่าตั้งต้น `"12.3.0"`
- `api_prefix` — ค่าตั้งต้น `"/v12.3"`
- `route_pins: dict[route, version]` — ค่าตั้งต้น `{"/signup/platform": "12.2.0"}`
  (แทน `SIGNUP_APP_VERSION` ที่ฮาร์ดโค้ดอยู่ตอนนี้ ซึ่งจะถูกลบ)
- `proven: set[(route, version)]` — route ไหนเคยได้ 200 ด้วยเวอร์ชันไหนแล้ว **ในโปรเซสนี้** (ไม่ลงไฟล์)
- `not_version: set[(route, version)]` — route ที่เคยสำรวจ 401 แล้วไม่เจออะไร (ไม่ลงไฟล์)
- `generation: int` — เพิ่มทุกครั้งที่สลับ ใช้ทำ single-flight (ข้อ 4.5)

**route** = path ที่ตัด prefix และ query ออก แล้วแทนทุก segment ที่มีตัวเลขด้วย `*`:
`/stage/enter/st01` → `/stage/enter/*`, `/mission/sevendays/receive/reward/123/attendance/1` →
`/mission/sevendays/receive/reward/*/attendance/*` ละเอียดพอจะแยก signup ออกจาก login
และไม่บวมตามเลขด่าน/seq

**User-Agent** ตามค่า App-Version ที่ส่ง (ปัจจุบัน UA ของ signup ค้าง 12.3.0 ขณะที่ App-Version เป็น
12.2.0 — ชุดที่วัดได้ 200 จริง) → ต้องพิสูจน์ด้วยการยิงจริงว่า signup ด้วย UA 12.2.0 ยังผ่าน
ถ้าไม่ผ่าน ให้ UA ใช้ `app_version` หลักเสมอแทน

### 3.2 ไฟล์ที่จำค่า

`src/api_version.json` ข้าง `config.ini` — engine_main เรียก `client_version.configure(<root>/src/api_version.json)`
ตอนเริ่ม (อินสแตนซ์หลักสร้างแบบ lazy จึงไม่สำคัญว่า tools ถูก import ไปก่อนแล้ว) เครื่องมือ CLI ใช้
env `LGRGS_VERSION_FILE` ถ้าตั้งไว้ ไม่งั้น `ratelimit.rl_dir()/api_version.json`

```json
{
  "app_version": "12.3.0",
  "api_prefix": "/v12.3",
  "route_pins": {"/signup/platform": "12.2.0"},
  "known_good": ["12.2.0", "12.3.0", "12.3.2", "12.4.0"],
  "history": [{"at": "2026-09-24 18:02:11", "what": "route_pin", "route": "/signup/platform",
               "from": "12.3.0", "to": "12.2.0", "why": "401 on never-proven route"}]
}
```

- อ่านครั้งเดียวตอนใช้ครั้งแรก ไฟล์ไม่มี → เขียนค่าตั้งต้นลงไป (ให้คนเปิดดู/แก้ได้) ไฟล์เสีย/อ่านไม่ได้
  → ใช้ค่าตั้งต้นทีละช่อง ห้ามทำให้ engine ล้ม
- เขียนทุกครั้งที่สลับ แบบ atomic: เขียนไฟล์ชั่วคราวชื่อไม่ซ้ำต่อโปรเซส/เธรด แล้ว `os.replace` ทับ
  (ลองซ้ำเมื่อ Windows ตอบ PermissionError) เขียนไม่ได้ → พิมพ์ลง stderr แล้วทำงานต่อด้วยค่าในแรม
  `history` เก็บ 20 รายการล่าสุด
- `known_good` = ทุกเวอร์ชันที่เคยได้ 200 ที่ไหนก็ตาม ใช้เป็นผู้สมัครอันดับแรกตอนสำรวจ

### 3.3 จุดที่ต้องต่อ — ทุกจุดที่ยิง rangers-api

| จุด | ตอนนี้ | หลังแก้ |
|---|---|---|
| `rangers_api.call` (ศูนย์กลาง: stage_forge, rewards, gifts, sevendays, tutorial, newbie_quest, flows) | `CLIENT_VERSION`, `API` | ห่อ attempt-loop เดิมเป็น `send(prefix, ver)` แล้วเรียก `client_version.request` พารามิเตอร์ `api=` เดิม → `pinned_prefix` |
| `gacha.call` | header ฮาร์ดโค้ด, path มี `/v12.3` ติดมา 7 ที่ | path ไม่มี prefix, ผ่าน `request` |
| `pull_roster.fetch_roster` + `ROSTER_PATH` | ฮาร์ดโค้ด | ผ่าน `request` |
| `new_account.game_login` / `signup_platform` | `APP_VERSION`, `SIGNUP_APP_VERSION`, URL ฮาร์ดโค้ด | ผ่าน `request` ลบ `SIGNUP_APP_VERSION` |
| `relogin.login` + `LOGIN_PATH` | `rangers_api.CLIENT_VERSION` | ผ่าน `request` |
| `device_session` (CLI อ่านจากเครื่อง) | ฮาร์ดโค้ด | ผ่าน `request` เพื่อความสม่ำเสมอ |

`rangers_api.API` และ `CLIENT_VERSION` ยังคงอยู่เป็นชื่อ (มีสคริปต์ CLI เก่าอ้างถึง) แต่ไม่มีใคร
ใน `tools/` หรือ `bot/engine/` ใช้มันส่งคำขออีก — ทดสอบด้วยการ grep ใน test

## 4. การไหลของข้อมูล

### 4.1 คำขอปกติ

`request` → อ่าน `(prefix, version)` สำหรับ route นี้ (pin ของ route ถ้ามี ไม่งั้นค่าหลัก) → `send` →
200 → บันทึก `(route, version)` ลง `proven` และ `version` ลง `known_good` (เขียนไฟล์เฉพาะตอน
`known_good` เปลี่ยน) → คืนผล **คำขอเดียว ไม่มีอะไรเพิ่ม**

### 4.2 จัดประเภทคำตอบ

| คำตอบ | ประเภท | การกระทำ |
|---|---|---|
| 400 + `errorCode 119801` | `VERSION_UNKNOWN` — ชัวร์ เพราะเช็กก่อนโทเคน | 4.4 สำรวจเวอร์ชันหลัก |
| 404 + `errorCode 400` | `ROUTE_MISSING` | 4.6 ตรวจว่า prefix ตายไหม |
| 401 และ `(route, version)` ไม่อยู่ใน `proven` และไม่อยู่ใน `not_version` | `SUSPECT_401` | 4.3 |
| 401 นอกจากนั้น | โทเคนตาย (เหมือนวันนี้) | คืนผลทันที ไม่ยิงเพิ่ม |
| อื่น ๆ | ปกติ | คืนผล |

### 4.3 กฎ 401 — วิธีแยก "เวอร์ชันโดนปฏิเสธ" ออกจาก "โทเคนตาย"

401 จะนับเป็นเรื่องเวอร์ชันก็ต่อเมื่อ route นี้ **ยังไม่เคยได้ 200 ด้วยเวอร์ชันที่เพิ่งใช้** ในโปรเซสนี้

- signup ไม่เคยได้ 200 ด้วย 12.3.0 → 401 แรก → ลองคำขอจริงซ้ำด้วยผู้สมัครทีละตัว เรียงจากใหม่ไปเก่า
  (ผู้สมัคร = `known_good` ลบตัวที่เพิ่งล้ม — ทุกตัวในนั้นเคยได้ 200 มาแล้วจึงไม่ต้องผ่าน oracle)
  → ตัวแรกที่ได้ 200 ถูกปักเป็น `route_pins[route]` และลงไฟล์ → คืนผล 200 นั้น
  วันนี้แปลว่า 12.4.0 → 401, 12.3.2 → 401, 12.2.0 → 200: คำขอเพิ่ม 3 ครั้ง ครั้งเดียวตลอดอายุไฟล์
- `/login` และ `/home` ได้ 200 ตั้งแต่บัญชีแรกของรัน → 401 ทุกครั้งหลังจากนั้นคือโทเคนตาย →
  **ค่าใช้จ่ายของ Login mode = 0**
- สำรวจแล้วไม่มีตัวไหนได้ 200 → ใส่ `(route, version)` ลง `not_version` แล้วคืน 401 เดิม —
  **ไม่ raise VersionUnavailable** เพราะ 401 ยังอาจเป็นโทเคนตายจริง ๆ route นี้จะไม่ถูกสำรวจซ้ำอีกในรันนี้
- ขอบเขต: สำรวจได้ครั้งเดียวต่อ `(route, version)` ต่อโปรเซส กรณีแย่สุดคือบัญชีแรกของรันมีโทเคนตาย →
  เสียคำขอเพิ่มเท่าจำนวนผู้สมัครที่รู้จัก (ตอนนี้ 3) ครั้งเดียว

การยิงคำขอเดิมซ้ำปลอดภัย เพราะ 401 / 119801 / route-missing ล้วนเป็นการปฏิเสธก่อนเซิร์ฟเวอร์ทำงานใด ๆ
(เหตุผลเดียวกับที่ `_do` และ `rangers_api.call` retry 429 อยู่แล้ววันนี้)

### 4.4 สำรวจเวอร์ชันหลัก (`VERSION_UNKNOWN`)

1. ผู้สมัคร = `known_good` + เวอร์ชันรอบค่าปัจจุบัน `M.m.p`: patch `M.m.0..M.m.5`, minor `M.(m-1).0` ถึง
   `M.(m+2).0`, major `(M+1).0.0` ตัดตัวที่เพิ่งล้มออก ไม่ซ้ำ
2. กรองด้วย oracle: `GET {prefix}/home` + `Cookie: LF_AC=0` + header ของผู้สมัคร → 119801 = ทิ้ง,
   401 = รู้จัก, อย่างอื่น = ไม่นับ
3. เลือก **ตัวใหม่ที่สุด** ที่รู้จัก (เวอร์ชันเดิมถูกเลิกแปลว่าเกมจริงใหม่กว่า) → ตั้งเป็น `app_version`
   → ลงไฟล์ → `on_switch` → ยิงคำขอเดิมซ้ำหนึ่งครั้ง
4. ไม่มีตัวไหนรู้จัก → `VersionUnavailable`

นับเฉพาะคำตอบที่ชัดเจน (119801 / 401 / 404) เป็นหลักฐาน ถ้า oracle เจอ network error หรือ 429/5xx
ระหว่างสำรวจ ให้ exception นั้นทะลุออกไปเป็นความล้มเหลวธรรมดาของบัญชีนี้ (retry ตามปกติของ flow)
**ห้ามนับเป็น "ไม่รู้จัก"** — เน็ตกระตุกช่วงสำรวจต้องไม่ทำให้ engine หยุดทั้งตัว

`route_pins` เดิมยังอยู่ ถ้าเวอร์ชันที่ปักไว้เองได้ 119801 ในภายหลัง pin นั้นถูกลบแล้วเดินตามข้อนี้

### 4.5 single-flight

128 เธรดอาจได้ 119801 พร้อมกัน `request` จำ `generation` ตอนเลือกค่า เมื่อเจอสัญญาณให้เข้า lock
แล้วเช็ก: ถ้า `generation` เปลี่ยนไปแล้ว (มีเธรดอื่นสลับให้แล้ว) → แค่ยิงซ้ำด้วยค่าใหม่ ไม่สำรวจซ้ำ
ถ้ายังไม่เปลี่ยน → เธรดนี้สำรวจ เธรดอื่นรอ lock ระหว่างสำรวจ oracle ยิงผ่าน lane bucket เดียวกับคำขอปกติ
(ไม่ผ่าน `request` เพื่อกัน recursion)

### 4.6 URL prefix (`ROUTE_MISSING`)

ตามที่ผู้ใช้เลือก: ย้ายเมื่อของเดิมพังเท่านั้น

1. oracle เช็ก `{prefix_ปัจจุบัน}/home` → 401 แปลว่า prefix ยังอยู่ แค่ endpoint นี้หายไป →
   **ไม่สลับ** คืน 404 เดิม (endpoint ถูกเลิกใช้ในเกม ไม่ใช่เรื่องของเรา)
2. ไม่ใช่ 401 → prefix ตาย → ผู้สมัคร `/v{M}.{m-1}` ถึง `/v{M}.{m+3}` และ `/v{M+1}.0` → oracle →
   เลือกตัวใหม่ที่สุดที่ตอบ 401 → ตั้ง `api_prefix` → ลงไฟล์ → `on_switch` → ยิงซ้ำ
3. ไม่มีตัวไหนตอบ 401 → `VersionUnavailable`

`pinned_prefix` (พารามิเตอร์ `api=` เดิมของ `rangers_api.call`) ไม่ถูกสลับ prefix เด็ดขาด

## 5. ถ้าไม่มีอะไรใช้ได้เลย — หยุด engine

`VersionUnavailable` เป็น `Exception` ธรรมดา (บทเรียนจาก `abd580e`: SystemExit ทำให้เธรดตายเงียบ)

- `flows.run_*` ต้อง **ปล่อยผ่าน** ก่อน `except Exception` ของตัวเอง — ไม่งั้นมันจะถูก retry
  `MAX_ATTEMPTS` ครั้งแล้วกลายเป็น `login failed`
- `EnginePool._run_one` ดักก่อน `except (Exception, SystemExit)`: `reporter.note(...)` ครั้งเดียว +
  `request_stop()` + **ไม่ย้ายไฟล์** (ค้างใน `execute/` แล้ว `queue.recover()` คืนเข้า `input/`
  ตอนรันถัดไป) ไม่นับเป็น done หรือ fail

เหตุผล: ถ้าปล่อยวิ่งต่อ Login จะย้ายไฟล์ input **ทั้งหมด** ไป `login failed/` และ GenID จะเผาโควตา mint
(2/นาที/IP) ทิ้งทุก attempt ทั้งคู่ต้องให้ผู้ใช้มาแก้ด้วยมือทีหลัง

## 6. มองเห็นได้

`engine_main` ลงทะเบียน `client_version.on_switch(reporter.note)` ทุกการสลับจึงขึ้นใน log ของ GUI เช่น

- `App-Version /signup/platform: 12.3.0 -> 12.2.0 (401 on a never-proven route)`
- `App-Version: 12.3.0 -> 12.4.0 (server no longer knows 12.3.0: 119801)`
- `API prefix: /v12.3 -> /v12.4 (/v12.3 no longer answers)`

พร้อมบรรทัดตอนเริ่ม: `api version: /v12.3 + 12.3.0 (pins: /signup/platform=12.2.0)`

## 7. การทดสอบ

**unit (ไม่แตะเซิร์ฟเวอร์)** — `FakeServer` ที่ตอบตามตารางข้อ 2 ทุกช่อง: เวอร์ชันที่รู้จัก, เวอร์ชันที่ signup
ยอม, prefix ที่มีอยู่, โทเคนดี/ตาย และนับจำนวนคำขอที่ได้รับ กฎ "ตัวปลอมต้องขาดสิ่งที่กำลังพิสูจน์":
เช่น เทสต์กฎ 401 ต้องใช้เซิร์ฟเวอร์ที่ signup ปฏิเสธ 12.3.0 แต่ `/home` ยอม

1. 200 ปกติ → เซิร์ฟเวอร์ได้คำขอ **1** ครั้งพอดี
2. 119801 → สลับเป็นเวอร์ชันใหม่ที่สุดที่รู้จัก → ยิงซ้ำสำเร็จ → ไฟล์อัปเดต → `on_switch` ถูกเรียก
3. signup 401 บน route ที่ไม่เคยผ่าน → ปัก 12.2.0 → ลงไฟล์
4. `/home` ผ่านแล้ว → 401 ครั้งถัดไป → เซิร์ฟเวอร์ได้คำขอ 1 ครั้ง (ไม่มีการสำรวจ)
5. 401 บน route ที่ไม่เคยผ่านแต่โทเคนตายจริง → คืน 401 เดิม ไม่ปัก และ 401 ครั้งที่สองบน route เดียวกัน
   → ไม่สำรวจซ้ำ
6. 404 route หายแต่ prefix ยังอยู่ → ไม่สลับ คืน 404
7. prefix ตาย → สลับเป็น prefix ใหม่ที่สุดที่มีอยู่
8. ไม่มีอะไรใช้ได้ → `VersionUnavailable`
9. 32 เธรดเจอ 119801 พร้อมกัน → oracle ถูกเรียกเท่ากับ **หนึ่ง** รอบสำรวจเท่านั้น
10. ไฟล์มี pin อยู่แล้ว → คำขอแรกใช้ค่า pin ไม่มีการสำรวจ
11. ไฟล์ไม่มี / JSON เสีย → ใช้ค่าตั้งต้น ไม่ล้ม
12. `pinned_prefix` ไม่ถูกสลับแม้ prefix ตาย
13. pool: `VersionUnavailable` → `request_stop` ถูกเรียก ไฟล์ **ไม่** ถูกย้ายไป `login failed/`
14. flows: `VersionUnavailable` ไม่ถูกกลืนเป็น retry
15. grep: ไม่มี `"12.3.0"` หรือ `"/v12.3` ในโค้ดที่ส่งคำขอใน `tools/` และ `bot/engine/`
    (ยกเว้นค่าตั้งต้นใน `client_version.py` และ docstring/comment)
16. oracle เจอ network error ระหว่างสำรวจ → exception เดิมทะลุออกมา **ไม่ใช่** `VersionUnavailable`
    และค่าปัจจุบันไม่ถูกเปลี่ยน

**พิสูจน์กับเซิร์ฟเวอร์จริง (ก่อนถือว่าเสร็จ)**

- (ก) ลบ pin ของ signup ในไฟล์ แล้วรัน GenID → ต้องหา 12.2.0 เจอเอง ได้บัญชี และเห็นบรรทัดสลับใน log
- (ข) ตั้ง `app_version` ในไฟล์เป็น 12.1.0 (ตายแล้ว) → ต้องฟื้นเอง
- (ค) รัน Login สั้น ๆ กับไฟล์ที่มีโทเคนตายปนอยู่ → oracle ต้องถูกเรียก 0 ครั้งหลังบัญชีแรก
- (ง) UA ตาม App-Version บน signup (ข้อ 3.1) — ยิงจริงหนึ่งครั้ง
- build .exe แล้ว `client_version` ต้องอยู่ใน bundle แบบถูกเข้ารหัส ไม่มี `.py` ข้าง exe

## 8. ข้อจำกัดที่รู้อยู่แล้ว

- oracle ใช้ `/home` เป็นตัวแทนทั้ง business tier ถ้าวันหนึ่งเซิร์ฟเวอร์ย้ายการเช็กเวอร์ชันไปหลังการเช็กโทเคน
  oracle จะตอบ 401 กับทุกเวอร์ชัน (ดูเหมือนรู้จักหมด) ผลคือเลือกผิดตัวได้ แต่คำขอที่ยิงซ้ำจะล้มอีก
  และจะจบที่ `VersionUnavailable` → engine หยุด ไม่ใช่วิ่งผิดแบบเงียบ
- ถ้า signup ปฏิเสธ **ทุก** เวอร์ชัน (เช่น appSecret บังคับทั้งหมด) กฎ 401 จะคืน 401 เดิม GenID ได้บัญชี
  `pending-login` เหมือนก่อน ระบบนี้แก้ปัญหาเวอร์ชัน ไม่ได้แก้ appSecret
- เวอร์ชันผู้สมัครสร้างจากเลขรอบค่าปัจจุบัน ถ้าเกมกระโดดไกลกว่านั้น (เช่น 12.3 → 14.0) จะหาไม่เจอ →
  `VersionUnavailable` ผู้ใช้เพิ่มค่าเข้า `known_good` ในไฟล์ด้วยมือได้
